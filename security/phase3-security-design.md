# FraudLens Phase 3 security requirements proposal

Prepared for Saumya and Riya on 24 November 2026 IST. Scope and migration approval are pending.

The current `users` table stores a global role, `transactions` uses a globally unique transaction ID, and scores and alerts reference that ID. The service token grants a single simulator ingestion identity. Dashboard queries, alert events, administrative audit views, and model operations all depend on the current global access model. A public account needs a tenant membership before accessing business data. ## Proposed contract and migration decisions

1. Approve account provisioning and global versus tenant capabilities in contract `2. Define current-session tenant switching, registration and recovery endpoints, key scopes, upload/export schemas, audit actor shapes, and tenant authorization errors in `8. In `6 specify whether models are shared platform artifacts or tenant-specific, and who can request drift, retrain or activation. [Current contracts](../docs/CONTRACTS.md#L45)
2. Approve `3 additions for organizations, memberships, invitations, verified email and reset state, session version, customer keys, import/export jobs and tenant ownership fields. Decide whether scores, alert keys, and account-history features use composite tenant keys or an internal globally unique row ID with tenant-enforcing foreign keys. Define the tenant identifier and producer/consumer compatibility rules for Kafka and alert events in `4. [Schema and events](../docs/CONTRACTS.md#L64)
3. Add nullable fields and tables first. Inventory existing data and agree explicit tenant attribution with the data owner. Quarantine ambiguous rows. Backfill under reviewed migrations, verify totals and ownership, add constraints and indexes, then cut over API, scoring, WebSocket and UI as a coordinated release. Reject requests without valid tenant context after cutover. Keep tenant enablement gated during the migration. Roll back compatible code only while the application can still enforce tenant boundaries. Retain mappings, memberships and audit evidence and follow the approved restore plan when a compatibility rollback would expose data.
4. Keep the existing Google and LinkedIn proposal separate. Confirm storage readiness, live provider behavior and provider-specific rollback before enabling public access. Require Riya and Saumya to approve any contract, schema or migration execution changes. [Existing OAuth rollout](social-oauth.md)

## S4 · GitHub sign-in option

After S2, Saumya can decide whether to add a dedicated GitHub OAuth App for identity-only sign-in. In GitHub Developer settings, register separate test and release applications with the approved first-party homepage and exact callback `https://<approved-origin>/api/auth/github/callback`. Proposed backend-only variables are `GITHUB_OAUTH_CLIENT_ID`, `GITHUB_OAUTH_CLIENT_SECRET` and `GITHUB_OAUTH_REDIRECT_URI` under the existing social feature flag. Amrita should surface the button only when the backend reports the provider ready. [GitHub web flow](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)

Use the confidential OAuth authorization-code exchange with S256 PKCE, exact callback validation, and the existing browser-bound single-use state pattern. GitHub's app web flow identifies the user by requesting the authenticated `/user` endpoint on receipt of each token. Request an empty scope set for that public profile and do not reuse a broadly authorized application. Map a fixed GitHub provider namespace and numeric user ID to the local user. Apply the same first-login ACTIVE VIEWER rule, local disabled status and authenticated explicit-link gate as other providers. Never persist the provider token, select identity by email or mutable login, or rely on GitHub's admin fields for a local role. [OAuth scopes](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps) · [Authenticated user API](https://docs.github.com/en/rest/users/users#get-the-authenticated-user)

Before enabling it, require fixture coverage for invalid and replayed state/code, wrong PKCE verifier, provider failure, login rename, identity collision, concurrent registration, explicit linking, disabled users and no privilege assignment. Review the attempt-table provider allowlist and verify existing Google, LinkedIn and password flows. Require an approved test registration and repeat login on the real callback origin.
